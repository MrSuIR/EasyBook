# EasyBook: постоянный контекст для агентов

Этот файл обязателен к учёту при любой работе в репозитории. EasyBook — backend
курсового проекта по базам данных на тему «Онлайн-сервис бронирования отелей».
Цель проекта — не просто CRUD, а демонстрация целостности данных, транзакций,
ролей, конкурентного бронирования и воспроизводимого запуска.

## Перед началом работы

1. Прочитай `README.md` — там описаны архитектура, ER-модель, endpoint-ы и запуск.
2. Проверь `git status`; не удаляй и не перезаписывай пользовательские изменения.
3. Для изменений схемы изучи всю цепочку `src/migrations/versions` и модели.
4. Не считай задачу законченной без соразмерной проверки тестами и статическим
   анализом.

## Технологии и границы

- Python 3.13, FastAPI, Pydantic 2.
- PostgreSQL, async SQLAlchemy 2, Alembic.
- JWT хранится в HttpOnly cookie.
- Изображения отелей сохраняются локально без фоновой обработки и ресайза.
- Pytest + Testcontainers, Ruff, Pyright, Docker Compose.
- В проект не входят frontend, платежи и настоящая email-рассылка.

Runtime-зависимости находятся в `requirements.txt`, инструменты разработки — в
`requirements-dev.txt`. Локальный интерпретатор проекта:
`venv/Scripts/python.exe` на Windows. Каталоги `venv`, `.idea`, кеши, `.env` и
пользовательские изображения не должны отслеживаться Git.

## Архитектура кода

- `src/api` — HTTP-маршруты, зависимости и проверка доступа.
- `src/service` — бизнес-правила и границы транзакций.
- `src/repositories` — запросы SQLAlchemy и блокировки БД.
- `src/models` — ORM-модели и ограничения схемы.
- `src/schemas` — публичные и внутренние Pydantic-контракты.
- `src/migrations` — единственный допустимый способ изменять существующую БД.
- `tests/unit_tests` — тесты без PostgreSQL и autouse DB fixtures.
- `tests/integration_tests` — тесты на временном PostgreSQL через Testcontainers.

Не помещай бизнес-логику в API-функции и не выполняй SQL напрямую из маршрутов.
API вызывает сервис, сервис координирует репозитории и делает `commit`.

## Неизменяемые бизнес-правила

### Пользователи и доступ

- Роли: `client` и `admin`.
- Публичная регистрация всегда создаёт `client`; передача роли запрещена.
- Email нормализуется в нижний регистр.
- Пароль имеет длину 8–72 символа.
- Клиент видит только свои бронирования.
- Администратор управляет отелями, номерами, удобствами и изображениями и может
  просматривать все бронирования.
- Login не возвращает JWT в JSON. Cookie должна быть HttpOnly, SameSite=Lax,
  ограниченной по времени и Secure в PROD.

### Бронирования

- `POST /bookings` принимает только `room_id`, `date_from`, `date_to`.
- Заезд разрешён не раньше текущей даты; `date_to` строго позже `date_from`.
- Интервалы полуоткрытые: `[date_from, date_to)`. Выезд и следующий заезд в один
  день не пересекаются.
- Цена копируется из номера в бронь в момент создания; `total_cost` считается по
  сохранённой цене.
- Отмена меняет статус на `cancelled` и заполняет `cancelled_at`, но не удаляет
  запись. Повторная отмена идемпотентна.
- Отменённая бронь сразу перестаёт участвовать в расчёте доступности.

Защита от овербукинга критична и не должна упрощаться. В одной транзакции:

1. тип номера блокируется `SELECT ... FOR UPDATE`;
2. считаются пересекающиеся брони со статусом `confirmed`;
3. количество сравнивается с `rooms.quantity`;
4. создаётся бронь либо возвращается `409 room_unavailable`.

Любое изменение этой логики должно сохранять тест: при 10 параллельных запросах
на единственный номер успешен ровно один.

### Целостность БД

- `rooms.price >= 0`.
- `rooms.quantity > 0`.
- `bookings.date_from < bookings.date_to`.
- Пара `(room_id, facility_id)` уникальна.
- Удаление отеля, номера или пользователя, на которые ссылаются брони, запрещено
  и даёт `409`.
- Связи номера с удобствами удаляются каскадно.
- PATCH с `facilities_ids=[]` полностью очищает удобства.
- Неизвестный facility ID даёт `404`.

Ограничения должны существовать одновременно на уровне Pydantic и PostgreSQL.
Не полагайся только на API-валидацию.

### Изображения

- Маршруты находятся под `/hotels/{hotel_id}/images`.
- Изменение изображений доступно только администратору.
- Допустимы JPEG, PNG и WebP размером до 5 МБ.
- Проверяются MIME и фактическое содержимое через Pillow.
- Исходное имя файла никогда не используется в пути; применяется UUID и каталог
  конкретного отеля.
- Сохраняется только проверенный оригинал; миниатюры и фоновая обработка не
  выполняются.

Изображения — дополнительная, а не центральная часть курсовой.

## Контракты API

Ошибки должны иметь единый вид:

```json
{"code": "machine_readable_code", "detail": "Описание или список ошибок"}
```

Используй следующие статусы последовательно:

- `400/422` — неправильные даты или входные данные;
- `401` — отсутствующий, повреждённый или истёкший токен;
- `403` — недостаточно прав;
- `404` — объект отсутствует;
- `409` — занятость или конфликт целостности;
- `429` — превышение rate limit;

Update/delete отсутствующего объекта не должен возвращать `200`. Списки отелей
и административных бронирований имеют формат `{items, total, page, per_page}`.

Глобальные обработчики ошибок находятся в `src/main.py`, доменные исключения — в
`src/exceptions.py`. Не возвращай произвольные несовместимые форматы ошибок из
отдельных маршрутов.

## Миграции

- Существующие пользовательские данные нужно сохранять.
- Не исправляй некорректные данные молча. Миграция должна остановиться с понятной
  ошибкой и описать, что необходимо исправить вручную.
- Новые ограничения добавляй после проверки существующих данных.
- Для удаления дублей сначала явно определи безопасное правило сохранения записи.
- У миграции должен работать downgrade.
- После изменения моделей и миграций проверь upgrade заполненной старой БД,
  создание чистой БД, `alembic check` и полный downgrade.

## Команды проверки

Из корня репозитория:

```powershell
.\venv\Scripts\ruff.exe check .
.\venv\Scripts\pyright.exe
.\venv\Scripts\pytest.exe
docker compose config --quiet
```

Для интеграционных тестов нужен запущенный Docker Desktop. `pytest` сам создаёт
временный PostgreSQL; не добавляй зависимость от вручную подготовленной тестовой
БД. Текущий эталонный набор содержит сценарии JWT, ролей, ограничений БД,
конкурентного бронирования, отмены, приватности и безопасных изображений.

Полный локальный запуск:

```powershell
docker compose up --build
```

Swagger: `http://localhost:8000/docs`.

Создание администратора:

```powershell
python -m src.cli create-admin --email admin@example.com
```

Команда идемпотентно повышает существующего пользователя или создаёт нового.

## Критерии готовности изменений

- Сохранены перечисленные бизнес-инварианты и разграничение ролей.
- Добавлены или обновлены тесты для изменённого поведения.
- Ruff, Pyright и релевантные тесты проходят.
- Миграции и Compose проверены, если изменение их затрагивает.
- В Git не попали `.env`, секреты, `venv`, `.idea`, `__pycache__`, `.pyc`, кеши
  тестов и загруженные изображения.
- README обновлён, если изменились запуск, архитектура или публичный API.
